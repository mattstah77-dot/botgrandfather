# Sequencing Laws

**Purpose:** Define evolution order and capability emergence rules  
**Status:** CANONICAL — Tier 1 Invariant  
**Version:** 1.0

---

## THE LAW

> **Evolution follows proven repetition. Capabilities emerge, they are not designed upfront.**

---

1. ✅ Dashboard aggregation (Capability Provider pattern)

## CAPABILITY EMERGENCE RULES

### Rule 1: Template Before Abstraction

**Template must exist and be proven before capability abstraction.**

```
❌ WRONG: Design CRM capability, then build CRM template.
✅ CORRECT: Build CRM template manually, extract capability after proven.
```

### Rule 2: Three Before Universal

**Three instances required before universal abstraction.**

```
❌ WRONG: Abstract customer viewing after 1 template.
✅ CORRECT: Customer viewing abstracted after lead-funnel, booking, and AI assistant.
```

### Rule 3: Manual Before Dynamic

**Manual registration before dynamic loading.**

```
❌ WRONG: Build plugin runtime before having 10 templates.
✅ CORRECT: Manual registration until 10+ templates prove need.
```

### Rule 4: Specific Before Generic

**Specific template before generic capability.**

```
❌ WRONG: Build "universal scheduling" before having 3 scheduling templates.
✅ CORRECT: Booking template implements own scheduling. Extract pattern later.
```

### Rule 5: Code Before Metadata

**Code implementation before metadata-driven configuration.**

```
❌ WRONG: Build metadata-driven workflow engine.
✅ CORRECT: Template implements flow in code. Extract metadata later if needed.
```

## SEQUENCING INVARIANTS

> **Invariant SL.1:** Template must exist and be proven before capability abstraction.

> **Invariant SL.2:** Three instances required before universal abstraction.

> **Invariant SL.3:** Manual registration before dynamic loading.

> **Invariant SL.4:** Specific template before generic capability.

> **Invariant SL.5:** Code before metadata.

> **Invariant SL.6:** Frontend follows backend API stability.

> **Invariant SL.7:** Tests follow critical path, not all paths.
